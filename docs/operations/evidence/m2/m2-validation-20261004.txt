## What executed tests establish

| Test | Executed scope and limits |
|---|---|
| `independent_exchange_and_negative_cases` | Four producer/consumer combinations (two same-provider controls, two independent directions). Different sender, recipient and wrong key. For every combination: wrong recipient, wrong signer, last ciphertext-byte flip, one-byte truncation and unknown receive profile reject. Each producer rejects unknown send profile. |
| `multiple_recipients_and_fresh_envelopes` | Each producer creates two different envelopes for two recipients. Both consumers decrypt/verify each recipient's first envelope (8 positive opens). Equality rejection shows fresh envelopes, not a standalone RNG/nonce audit. |
| `rpgp_generated_certificate_exchange` | Both sender/recipient roles use independently generated Sequoia/rPGP certificates, both seal APIs and both open APIs (8 positive opens). Explicit rPGP v6, certify/sign flags and SEIPDv2 feature are required. |
| `both_composite_signature_components_required` | Each provider generates a detached v6 SHA-512 composite signature; both verify it. Flip one byte of provider-parsed Ed25519 material, then separately ML-DSA material: both verifiers reject both mutations for both producers (8 component-negative checks). Changed signed content also rejects. No fabricated serializer or unrelated signature substitutes for these tests. |
| `unsupported_certificates_and_limits` | Both seal APIs reject classical cert, malformed recipient bytes, recipient secret bytes and >1 MiB plaintext; both open APIs reject malformed and >1 MiB wire input. Not exhaustive parser fuzzing or product-limit qualification. |
| `native_version_and_published_signature_vector` | Runtime native version; RFC9980 A.3.2/A.3.4 signature verifies in both providers; changed known vector input rejected by rPGP. The text vector uses provider canonicalization, unlike generated binary signatures. |
| `published_kem_message_vector_rpgp` | RFC9980 A.3.1/A.3.3 known encrypted message decrypts and its signature verifies in rPGP before expected bytes are compared. Original vector algorithms are retained; this is not the generated SHA-512/GCM profile or an independent exchange. |
| `pgp_mime_protected_header_fixture` | Both producers/consumers use RFC3156 two-part armored combined sign/encrypt wrapper and RFC9788 protected fields. Normal and forged outer Subject produce identical verified inner fields (8 positive opens). Outer subject does not expose generated inner subject. Common MIME parser/wrapper; no mail client, SMTP, render/reply or Bcc evidence. |
| `rpgp_rng_failure_returns_no_result` | Injected RNG panics during rPGP composite key generation and encrypted builder creation. `catch_unwind` observes no result. This identifies panic behavior, not a typed error. No selected-backend health/self-test or OS entropy fault is simulated by this test. |

Recipient public export is reparsed and asserted to contain no secret material;
both encryption entry points reject secret recipient blobs. The test harness
owns all ephemeral keys, but the sender functions receive only recipient public
bytes. This establishes an API boundary, not two-machine isolation or identity
verification. The two implementations have different OpenPGP parsers and PQ
backends; the experiment shares an outer Sequoia policy precheck and MIME wrapper.
That shared precheck is not independent adversarial-parser assurance.

Both open adapters collect private output in memory, read to EOF and complete
provider integrity/signature checks before returning success. On any error the
buffer is dropped; there is no streaming output/callback, log or persisted file.
No secure-zeroization claim. Provider streaming APIs themselves can emit chunks
before final verification; callers must preserve this buffering boundary.

## Header/profile boundary

§54 explicitly requires an AEAD/header-profile fixture in M2, so raw OpenPGP
packets alone were insufficient. The isolated fixture now covers the choice:
RFC3156 §2 ASCII armor and §6.1 combined signing/encryption; RFC9788 §§2.1–2.2
`hp="cipher"` plus protected copies of exposed nonstructural outer fields.
The candidate selects GCM, a protected experimental profile marker and a generic
outer Subject. The marker does not replace packet validation or identity checks.

This is a **bounded fixture**, not a full RFC9788 conformance claim. Comprehensive
malformed/duplicate headers, critical extensions, attachment names/types,
reply/reference fields, intended-recipient rules, Bcc, replay and legacy display
elements need M5/M6 integration evidence under §§42/54. No independent PQ mail
client rendered this fixture. M2 must decide the compatible provider/crypto/header
approach now; production MIME implementation remains M5, safe display/replies M6.

## Failures retained and corrections

Earlier experiment setup failures are not erased: the initial Sequoia RustCrypto
attempt had incompatible `ml-kem` trait dependencies; final backend selection is
explicit OpenSSL, not a silent downgrade. Git's bundled Perl lacked a required
module; pinned portable Strawberry Perl was used. Missing/wrong libclang path was
corrected. Initially considered OpenSSL 3.5.5 was abandoned before qualification
in favor of explicitly recorded 3.5.9. No production lock was changed.

Initial four-test harness failed for absent signing flags and treating a framed
signature packet as a packet body. These were corrected through provider APIs;
the fourth run passed 4/4. Expanded run: 5 passed/2 failed, due to low-level text
signature verification without canonicalization and rPGP's default missing
SEIPDv2 capability. Provider streaming text verification and explicit generated
certificate capabilities corrected these; 7/7 then passed. The first MIME wrapper
used bare base64; standards inspection required ASCII armor, now tested. The
eight-test run passed; adding the known encrypted vector initially used the wrong
rPGP constructor name (compile error), corrected to `Message::from_armor`.
These are harness/API corrections, not assertion weakening or hidden test skips.
